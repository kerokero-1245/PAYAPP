# ADR-0001: DDD レイヤリングの採用

- ステータス: 承認
- 日付: 2026-07-05

## 背景

ビジネスルール（カートの数量下限、合計計算、注文確定、価格整形など）が
Zustand ストア内に散在し、UI・永続化・ルールが密結合していた。
テストしづらく、機能追加時の影響範囲も読みにくい。

## 決定

ドメイン駆動設計（DDD）に基づき、ビジネスルールを純粋な `domain/` レイヤへ集約する。

- 境界づけられたコンテキスト: `shared` / `catalog` / `cart` / `ordering`
- 依存の向きは常に内側（ドメイン）へ。ドメインは React/Next/Zustand/Stripe を知らない
- 副作用（時刻・ID 採番）は**ポートとして注入**（例: `OrderClock`）
- ドメイン層は TypeScript で記述し、値オブジェクトと不変条件を型で表現する
  （`tsconfig` は `allowJs` のため既存 JS と共存可能）

## 結果

- ルールが一箇所に集約され、単体テストで仕様を固定できる
- ストアは「状態保持と配布」に徹するインフラ層になる
- `toJSON()/fromJSON()` が既存 localStorage スキーマと一致し、移行コストなしで委譲できる
- トレードオフ: レイヤと変換（DTO ⇄ ドメイン）が増える。小さなプロジェクトには一見過剰だが、
  EC はコンテキストが自然に分かれ、ルールが育つ領域のため妥当と判断
